# Time Series Forecasting: Baselines and Backtests

Seven scripts on one question: **when the future of something is decided only by its own
past, how do you predict it — and how do you know whether the prediction is any good?**

The path runs from pulling a series apart, through the statistical models
(AR, MA, ARMA, ARIMA, SARIMAX in `statsmodels`), through an additive decomposable model
(`prophet`), through a windowed recurrent network (`torch`), and ends at a method that is
not even a regression: a product of group averages. On the panel used here, that last one
wins.

Every series in this module is **generated by `01_build_time_series_datasets.py` from a
mechanism written down in the file**, and every generator writes its parameters to
`data/ground_truth.json`. That is the whole design: it makes "did the method recover it"
and "by how much did it miss" into questions with answers, rather than into pictures that
look about right.

The module runs entirely offline. No API key, no download, no network call.

**Requires**: `statsmodels`, `prophet`, `torch`, `pandas`, `numpy`, `matplotlib`.

---

## 1. What this module is about

### 1.1 The proposition

**When the future of a quantity is decided only by its own past, use a time series model.
When it is decided by a pile of external factors, use a regression model.**

This module is about the first kind, and it keeps returning to one point: the first kind is
a **baseline**, not a destination.

### 1.2 Time series against regression

| | Regression | Time series |
| :--- | :--- | :--- |
| **What is modelled** | The relation between a target y and one or more inputs x | The relation between a target y and **time** |
| **How it predicts** | Feed it a new x, get a y | Feed it y's own history, get the next y |
| **Good at** | Many variables against one outcome | Trend, cycle, phase and instability of one quantity |
| **With a single variable** | Still usually **has nothing to do with time** | **Built on top of time** |

In one sentence: **a time series model is a regression whose only input is the series
itself.**

### 1.3 When not to use one

Take daily unit sales for five thousand stores. The things that plausibly matter:

1. sales history
2. weather
3. store
4. promotions
5. events

**Only the first is available to a time series model. The other four need a regression.**
In a setting where a working model carries fifty-odd factors, a single-input model cannot
walk on one leg.

### 1.4 Using both

The two routes divide like this:

```
Route 1: time series  -> a fast baseline -> ARIMA
Route 2: regression   -> many variables (time, promotions, item count, budget, purchasing power)
                      -> gradient boosting; neural networks
```

And they compose: **the output of a time series model can be fed to a regression as one
more feature.**

### 1.5 Where a time series model sits in a project

A cross-domain rule of thumb: **as a baseline, a time series model reaches roughly a third
to two fifths of what a well-worked solution reaches.** It is fast, it is simple, and the
answer is usable.

The room above that is not in a fancier model. It is in **feature engineering and in the
choice of data** — and in a time series, *choosing which stretch of data to train on* **is**
the feature engineering. Section 10.4 prices that choice on a real split.

### 2.1 The cash-flow panel: two cycles, and one of them is a rule

Both columns are a product of the same three ingredients:

```
value = base level  x  weekday factor  x  day-of-month factor  x  noise
```

The two weekday profiles are constants at the top of the file:

```python
# Inflow peaks early in the working week and collapses at the weekend.
PURCHASE_WEEKDAY = np.array([1.16, 1.21, 1.11, 1.04, 0.94, 0.71, 0.75])
# Outflow peaks on Monday instead, and its weekend dip is shallower.
REDEEM_WEEKDAY   = np.array([1.22, 1.09, 1.04, 1.01, 0.97, 0.81, 0.84])
```

**The weekend collapse is not decoration; it is what a settlement rule does to a cash
flow.** When interest starts accruing only from the next business day, a transfer made on
Friday, Saturday or Sunday earns nothing until the following week. Two weekend days are
therefore dead on the inflow side, and the demand they would have carried piles up on
Monday. **The rule produces the cycle. It is not a coincidence in the data.**

The month-position factor is a lookup rather than a formula, so that a fitted factor can be
compared against it entry by entry:

```python
def day_of_month_factor(day: int) -> float:
    """Return the month-position factor for one calendar day.

    Money moves at the edges of a month and sits still in the middle: the first
    three days and the last two carry the payroll and settlement peaks, and the
    middle of the month is the trough.
    """
```

Day 1 is `1.34`, day 13 is `0.89`, day 31 is `1.26`. **Edges high, middle low.**

Two more terms go onto the outflow column only:

```python
REDEEM_DAILY_GROWTH = 0.0007       # a steady growth rate
REDEEM_RANDOM_WALK_SIGMA = 0.035   # a level that never returns to where it started
```

They are built separately on purpose. **The second one, not the first, is what makes a
unit-root test fail** — and section 4.6 turns that distinction into a measurement.

Finally, four dates get a lift no cycle can explain:

```python
CAMPAIGN_DAYS = ["2013-11-11", "2013-12-12", "2014-06-18", "2014-08-08"]
CAMPAIGN_LIFT = 1.55
```

These are the events section 7.11 asks a model to recover.

## 3. Decomposition: one curve into three

### 3.1 The split

`statsmodels`' `seasonal_decompose()` returns three parts: **trend**, **seasonal** and
**residual**. A minimal call needs five steps:

| Step | What | Why |
| :--- | :--- | :--- |
| 1 | Read only the date column and the value column | The rest is not used by the split |
| 2 | Parse the dates **and set them as the index** | The split reads the index to place the cycle |
| 3 | Coerce the values to numbers | A CSV column can arrive as strings |
| 4 | **Interpolate gaps** | The split does not accept NaN, and non-trading days leave holes |
| 5 | `seasonal_decompose(series, period=N)` | `period` is the only parameter to choose |

`STL` is the robust version of the same idea. The difference is that **it lets the cycle
change shape over time**, where the moving-average method holds it fixed.

### 3.2 Choosing the period

**The question is how many rows one full cycle occupies, not how many days there are in a
year.** For a series of business days with an annual cycle, that is roughly **250**, not
365. Using 365 stretches the cycle over about one and a half years and destroys the pattern
it was supposed to find.

### 3.3 Reading the result

A useful shape to expect on a market series: the seasonal component swings by a small
amount, the residual by a large one. When the residual dominates the cycle by an order of
magnitude, that is the quantitative version of "shocks are not predictable" — and it is why
an autoregressive forecast on such a series can only *follow*.

### 3.4 Measured: can the planted cycle be recovered

`02_decompose_and_stationarity.py` runs the split at the planted period and at three wrong
ones:

| `period` | Correlation with the planted cycle | Recovered half-amplitude | Remainder sd |
| ---: | ---: | ---: | ---: |
| **250** (planted) | **+0.9981** | 0.0617 | 0.01293 |
| 60 | +0.0002 | 0.0026 | 0.01251 |
| 288 | +0.0540 | 0.0115 | 0.04760 |
| 500 | +0.9941 | 0.0651 | 0.01793 |

**Every run returned a seasonal component. Only one of them tracks the cycle.**

The scoring function says why correlation is the criterion:

```python
def score_seasonal(recovered: pd.Series, planted: np.ndarray) -> tuple[float, float]:
    """Return the correlation between a recovered cycle and the planted one, and its amplitude.

    Correlation is the criterion rather than a plot, because a decomposition
    always returns a seasonal component of the length it was asked for: the
    component exists whether or not a cycle of that length is in the data.
    """
```

**500 also scores +0.9941**, because 500 is an exact multiple of 250 and the two stay in
phase. **A high correlation is necessary and not sufficient** — the amplitude and the
remainder have to be read next to it.

### 3.5 Robust against moving average

Same series, both methods:

| Method | Correlation | Half-amplitude | Remainder sd |
| :--- | ---: | ---: | ---: |
| STL (robust) | +0.9849 | 0.0837 | 0.01671 |
| Moving average | +0.9981 | 0.0617 | 0.01293 |

On a series whose cycle genuinely never changes, the method that holds the cycle fixed wins.
**Robustness is not free accuracy; it buys tolerance for a cycle that drifts,** and here
there is no drift to tolerate.

## 4. Stationarity and differencing

### 4.1 The augmented Dickey-Fuller test

An autoregressive model wants a stationary series, so the first question asked of any
series is whether it is one.

**The null hypothesis is that the series has a unit root** — that is, that it is *not*
stationary. A small p-value is therefore the good news: it is evidence against a random
walk.

```python
def adf_report(series: pd.Series, label: str) -> float:
    """Run an augmented Dickey-Fuller test and print the parts that get misread.

    Printing the statistic next to the critical values matters because a p-value
    alone hides how close the call was.
    """
    stat, p_value, used_lag, nobs, crit, _ = adfuller(series.dropna(), autolag="AIC")
```

A real line of that output:

```
inflow, as generated               stat    -4.776  p   0.0001  lags 14  n  169  -> stationary
                                   critical  1% -3.470  5% -2.879  10% -2.576
```

> **The direction of "smaller" is where this is misread.** The statistic is **negative**.
> "Smaller than the critical value" means **more negative** (-5.16 < -3.45).
> **More negative means more stationary.**

### 4.2 KPSS: the same question with the null reversed

```python
def kpss_report(series: pd.Series, label: str) -> float:
    """Run a KPSS test, whose null hypothesis is the reverse of the previous one.

    Running both is what turns a single borderline p-value into an agreement or a
    disagreement, and a disagreement is itself information: it usually means the
    series is neither clean noise nor a clean random walk.
    """
```

KPSS assumes stationarity and looks for evidence against it, so its verdict reads the other
way round. **Its p-values are interpolated in a lookup table that stops at 0.01 and 0.10**
and it warns whenever a statistic falls outside that range — so read the number as a side of
a boundary, not as a measurement. The script suppresses that specific warning and says so:

```python
# The lookup table this test interpolates in stops at 0.01 and 0.10, and it
# warns whenever a statistic falls outside that range. Every call here does,
# which is the point being reported below rather than something to fix.
```

### 4.3 Differencing

**Differencing is subtracting each element from the next one**, to remove the influence of
the level. Take `f(x) = x²`:

| Stage | Series | Stationary |
| :--- | :--- | :--- |
| Original | `1, 4, 9, 16, 25, ...` | No — a quadratic trend |
| First difference | `3, 5, 7, 9, 11, ...` | No — a linear trend remains |
| Second difference | `2, 2, 2, 2, ...` | Yes |

**The test is whether the differenced series becomes a flat line.** The general rule: a
polynomial of degree d needs at most **d** differences, because **each difference lowers the
degree by one**.

### 4.4 Undifferencing, and why forgetting it is fatal

| Step | What |
| :--- | :--- |
| 1 | **Keep the initial value** (the first term before each difference) |
| 2 | Reverse the operations in order — differencing subtracts, undifferencing adds |

```
second difference   2, 2, 2, ...
    + the first term of the first difference (3)
first difference    3, 5, 7, 9, ...
    + the first term of the original series (1)
original            1, 4, 9, 16, 25, ...
```

**Why this cannot be skipped**: the model was trained on the differenced series, so what it
emits is a *change*, not a *level*. Without the reverse operation the forecast is not in the
same units as the thing being forecast. Section 10.5 carries the practical consequence: a
submission short by two orders of magnitude scores zero.

The size of the effect, measured on one differenced cash-flow column:

| | Before | After one difference |
| :--- | ---: | ---: |
| **Mean** | 274,793,920 | **446,251** |
| **Standard deviation** | 90,900,137 | 101,343,101 |

**The mean drops by a factor of 616. The standard deviation barely moves, and even rises.**
⇒ **Differencing removes the trend, not the variability.**

### 4.5 How many differences: the smallest one that passes

`02` runs three orders on the same column:

| Series | sd | ADF p | Verdict |
| :--- | ---: | ---: | :--- |
| d=0 | 93,197,206 | 0.0299 | stationary |
| d=1 | 85,194,988 | 0.0000 | stationary |
| d=2 | 130,537,676 | 0.0000 | stationary |

**A test can say a series is differenced enough. It can never say it is differenced too
much** — all three pass. And d=2 inflates the spread by **1.53x**, handing the model extra
noise to fit.

⇒ **The order of differencing cannot be settled by the test alone.** Section 6.7 puts the
question on a holdout, and the answer there is not the one this section sets up.

### 4.6 Measured: a strong cycle hides a wandering level

This is the finding that overturned the assumption it started from.

The generated outflow column **does carry a random walk** — its level never returns. The ADF
test calls it stationary anyway, disagreeing with the generator. So the script isolates the
cause with a Monte Carlo in which **every series is a random walk, and therefore every
"stationary" verdict is a mistake**:

| What the test is shown (300 draws of 184 rows each) | Wrong |
| :--- | ---: |
| The walk on its own | **9%** |
| The same walk under the weekday and month-position cycles | **28%** |
| The same walk with those cycles divided back out | **9%** |

**Laying the cycles over a walk multiplies the error rate by 3.1x, and removing them undoes
it.** It is not the sample size; it is the cycles.

The mechanism: a strong deterministic cycle reads, in the test's own regression, as strong
mean reversion. The test sees "it always comes back" — and what comes back is the position
within the week, not the level.

⇒ **Decompose first, then test.** A stationarity test run on the raw column is answering a
different question.

> Stated honestly: after dividing the cycles out, this particular column is *still* called
> stationary. The first row of the table above is why — on a clean walk at this length the
> test is wrong 9% of the time, and this column is one of those times. **Removing the cycle
> makes the verdict worth reading. It does not make a 184-row verdict conclusive.**

## 5. The autoregressive family

### 5.1 AR: regressing a series on itself

**AR = Auto Regressive.** The simplest linear time series model: build a regression equation
from the relation between earlier values and later ones.

**The idea**: a **linear combination** of the values at the previous few time points, plus
**white noise**, predicts the value at the next one.

$$x_t = \phi_1 x_{t-1} + \phi_2 x_{t-2} + \dots + \phi_p x_{t-p} + u_t$$

**AR(p)** is a p-th order autoregressive process, **φ** are the autoregressive coefficients,
**u_t** is white noise. At p=1 it reads: **the current value depends only on the previous
one.**

### 5.2 White noise

> White noise exists in ordinary life. In modelling it can be read as
> **a purely random process with expectation 0 and constant variance.**

The plain-language version of "expectation 0": **the fluctuations cancel each other, so they
accumulate to nothing.**

### 5.3 MA: regressing on the shocks instead

**MA = Moving Average.** Nearly the same shape as AR, with one substitution:

> An AR model is a linear combination of **past values of the series**;
> an MA model is a linear combination of **past white noise**.
> The past noise reaches the present **indirectly, through the values it already moved**.

$$x_t = u_t + \theta_1 u_{t-1} + \theta_2 u_{t-2} + \dots + \theta_q u_{t-q}$$

**The analogy that makes MA click**: let X_t be the price on day t and U_t be the news on
day t. Today's price is moved by today's news, and also by yesterday's news — **but less, so
the older term carries a coefficient.**

That one comparison settles two things at once: **why the input is noise rather than past
prices** (the noise *is* the external shock), and **why the coefficients decay** (older news
moves less).

**Order notation**: AR uses **p**, MA uses **q**. That is the basis for ARMA(p,q) and
ARIMA(p,d,q).

> **Symbol convention**: the standard is **φ for AR coefficients and θ for MA
> coefficients.** Some write-ups swap the two symbols in the combined equation; that is a
> typesetting reuse and does not change the model.

### 5.4 ARMA: both halves

**ARMA = Auto Regressive Moving Average.** It estimates better than either half alone,
and carries both orders.

**Why mixing helps**:

> AR handles the relation between current and later values; MA handles the random
> variation, that is, the noise.

⇒ Each half does one job: **AR carries memory, MA carries shocks.** On a financial series:
**price momentum comes from AR, event shocks come from MA.**

**Degenerate cases**: q=0 gives AR(p), p=0 gives MA(q). ARMA is the one used most often.

### 5.5 ARIMA and its four steps

**ARIMA = Auto Regressive Integrated Moving Average.** In one line:
**difference the non-stationary data until it is stationary, then run ARMA on it.**

The mechanics are identical to ARMA; the order becomes a triple **(p, d, q)** where **d is
the number of differences**.

| Step | What |
| :--- | :--- |
| **1** | Look at the series and decide whether it is **stationary** |
| **2** | If not, take **d differences** to make it so |
| **3** | Fit ARIMA(p, d, q) and **search for the best (p, d, q)** |
| **4** | Predict, and **reverse the differencing** |

### 5.6 How the four relate

**AR and MA are special cases of ARMA; ARMA is a special case of ARIMA.**

| Model | Equivalent |
| :--- | :--- |
| AR(p) | ARMA(p, 0) |
| MA(q) | ARMA(0, q) |
| ARMA(p,q) | ARIMA(p, **0**, q) |
| ARIMA(p,d,q) | the general form |

**This matters in practice**: current `statsmodels` has no standalone `ARMA` class.
**To fit an ARMA, write `ARIMA(data, order=(p, 0, q))`.**

### 5.7 Version notes for the current libraries

Several interfaces in this area changed, and code written against the older ones fails at
import rather than at runtime. What the scripts here use:

| Concern | Current form |
| :--- | :--- |
| ARIMA / ARMA | `from statsmodels.tsa.arima.model import ARIMA`; `statsmodels.tsa.arima_model` no longer exists |
| Seasonal ARIMA | `sm.tsa.statespace.SARIMAX(...)` |
| Decomposition period | `seasonal_decompose(..., period=250)`; the `freq=` keyword is gone |
| Label slicing | `.loc[...]`; `.ix` was removed from pandas |
| Resampling aliases | `resample("ME")`, `"QE"`, `"YE"`; pandas 3 dropped `"M"`, `"Q-DEC"`, `"A-DEC"` |
| Additive model package | `from prophet import Prophet` |

Two parameters worth naming, since both appear in the constructors:

| Parameter | Full name | Meaning |
| :--- | :--- | :--- |
| **endog** | endogenous variable | The variable the model determines — the thing being analysed |
| **exog** | exogenous variables | Variables driven from outside the model, not the object of study |

### 5.8 SARIMAX, and one thing it does not do by itself

`SARIMAX` is a superset of ARIMA — **S for Seasonal, X for eXogenous**.

> **Using the seasonal class is not the same as using seasonality.**
> Passing only `order=(p,d,q)` and leaving `seasonal_order` unset degenerates it into an
> ordinary ARIMA. **The criterion is whether `seasonal_order` was passed, not which class
> was imported.**

Two switches that usually travel with it:

```python
sm.tsa.statespace.SARIMAX(series, order=order, seasonal_order=seasonal,
                          enforce_stationarity=False, enforce_invertibility=False)
```

They turn off the stationarity and invertibility checks. With the checks on, many candidate
orders raise instead of fitting; with them off, a whole grid completes — **at the cost of
possibly selecting a numerically unstable model.**

## 6. Searching a grid by information criterion

### 6.1 AIC

> **The Akaike Information Criterion measures how well a statistical model fits.
> Smaller is better.**

$$\text{AIC} = 2k - 2\ln(L)$$

with $k$ the number of parameters and $L$ the likelihood. **The first term penalises
complexity, the second rewards fit.**

That is the answer to "how are p and q chosen": **enumerate the combinations and take the
smallest AIC.** The orders have no theoretically optimal value; they are hyperparameters.

> **AIC grows with sample size**, so a value from 90 points and a value from several hundred
> **cannot be compared to each other**. Only values on the same data are comparable.

### 6.2 The search, and what it has to report

```python
def search_orders(series: pd.Series, candidates: list[tuple[int, int, int]],
                  seasonal: tuple[int, int, int, int] | None = None) -> pd.DataFrame:
    """Fit every candidate order and return the whole table, not only the winner.

    Returning the full table is the point. A search that reports one order and
    one score cannot be checked: the reader cannot see how many candidates were
    tried, whether any failed to converge, or how close the runner-up was. All
    three of those change what the winning order is worth.
    """
```

The mechanics are conventional — a Cartesian product of ranges, a running best, a
`try/except` around each fit so that a non-converging combination is skipped instead of
killing the loop. **What is not conventional is returning the table.**

> A bare `except:` is worse than `except ValueError`: it swallows every error, including a
> misspelled attribute. If all candidates fail, the following line raises `NameError` with
> no trace of the real cause.

### 6.3 Measured: AIC ranks fits, it does not identify mechanisms

`03_arima_grid_search_and_forecast.py` searches sixteen orders on a series generated from a
**fixed ARMA(2, 0, 1)**:

| Order | AIC | Gap to best |
| :--- | ---: | ---: |
| (1, 0, 3) | 5009.77 | 0.00 |
| (3, 0, 3) | 5009.90 | 0.13 |
| **(2, 0, 1)** — planted | 5010.64 | 0.88 |
| (3, 0, 0) | 5011.46 | 1.69 |

**The search did not return the planted order**, and the top four sit inside 2 AIC of each
other.

So the script converts each fit back into a process and compares autocorrelations:

| Order | AIC | Max ACF gap to planted, lags 1-12 |
| :--- | ---: | ---: |
| (1, 0, 3) | 5009.77 | 0.0827 |
| (3, 0, 3) | 5009.90 | 0.0724 |
| (2, 0, 1) | 5010.64 | 0.0494 |

**The top orders carry almost the same autocorrelation as the planted recursion, written
with different numbers of terms.**

⇒ **An information criterion ranks fits; it does not identify a mechanism.** What was
recovered is the dynamics, not the order label. Reporting "we recovered ARMA(2,0,1)" would
be a claim the run does not support; reporting "the top four are within 2 AIC and share the
dynamics" is what it does support.

### 6.4 Truncating the candidate list

A common way to make a search finish sooner:

```python
parameters = list(product(p, d, q, P, D, Q))[:20]   # keep the first twenty
```

**`[:20]` is not a sample of twenty. It is the first twenty in lexicographic order.**
`itertools.product` varies the last factor fastest, so slicing the front of the list holds
the **first** factor near its smallest values.

Measured on the monthly table, full grid against the truncated one:

| | Candidates | Range of p | Winner | AIC |
| :--- | ---: | :--- | :--- | ---: |
| Full grid | 40 | [0,1,2,3,4] | **(4, 0, 0)** | 187.45 |
| Truncated | 20 | [0,1,2] | **(0, 0, 3)** | 189.68 |

**Of the twenty candidates never fitted, the best was (4,0,0) — ranked first overall.**

⇒ **Both runs print a best AIC, and nothing in that number says which orders were never
tried.** The candidate count has to be printed next to the winner, or the two runs are
indistinguishable to a reader.

### 6.5 In-sample and out-of-sample

- **`predict()`** returns point estimates
- **`get_prediction()`** returns an object carrying both **`.predicted_mean`** and
  **`.conf_int()`** — needed for an interval band

> **The most common fake backtest**: call `get_prediction(start=-30)`, score the last thirty
> observations, report an RMSE. But the model was fitted on data **that included those
> thirty**. That is goodness of fit, not a backtest.

Measured on the same series:

| | RMSE |
| :--- | ---: |
| Last twelve months, fitted by a model **that saw them** | 5.78 |
| Last twelve months, forecast by a model **that did not** | 6.37 |

**Only the second number describes a forecast.**

### 6.6 Reading one series at four scales

```python
scales = {"day": index,
          "month":   index.resample("ME").mean(),
          "quarter": index.resample("QE").mean(),
          "year":    index.resample("YE").mean()}
```

| Scale | Points | sd/mean | Largest step |
| :--- | ---: | ---: | ---: |
| day | 7145 | 0.299 | 0.067 |
| month | 330 | 0.301 | 0.074 |
| quarter | 111 | 0.306 | 0.152 |
| year | 29 | 0.329 | 0.207 |

**The yearly series has 29 points — too few to fit anything with a memory of seven.**

⇒ **Aggregating is not free smoothing: it deletes every cycle shorter than the new step.**
Monthly is often the level modelled rather than daily, because **the daily jitter drowns the
trend.**

### 6.7 Building future dates

A very common hand-rolled loop: take the number of days in the current month, add it to the
cursor, repeat.

```python
def month_ends_by_day_count(last: pd.Timestamp, count: int) -> list[pd.Timestamp]:
    """Step forward by the length of the current month, repeatedly.

    This is the arithmetic that reads as obviously correct and is not. Adding
    the length of the month the cursor is standing in lands it inside the next
    month rather than on the same position in it, and the error accumulates.
    """
```

`03` audits it over 365 starting dates, six steps each:

| Check | Sequences |
| :--- | ---: |
| With a repeated date | **0** |
| Visiting one calendar month twice | **0** |
| **Missing the month end at least once** | **365** |

**The failure is not duplicate dates. It is labels that drift off the period they are
supposed to name.** From 30 June, six steps give `07-30 / 08-30 / 09-30 / 10-30` where the
real month ends are `07-31 / 08-31 / 09-30 / 10-31` — **three of four are a day out.**

The fix is a date offset, and two assertions:

```python
by_offset = pd.date_range(last, periods=FORECAST_MONTHS + 1, freq="ME")[1:]

assert len(set(by_offset)) == len(by_offset), "forecast dates must be distinct"
assert all(d == d + pd.offsets.MonthEnd(0) for d in by_offset), \
    "forecast dates must land on month ends"
```

> **Why these have to be assertions**: forecast values carry no date of their own. A wrong
> label is attached silently, and it survives every join and every write.

**A worse variant of the same class**: a loop that pushes `last_date + i` forward to the
next business day pushes **several different i to the same day**. Seven forecast steps land
on five distinct dates, and because the values are written by position, **later writes
overwrite earlier ones and the whole series shifts by one from the second day onward.** The
only visible symptom is a repeated date in the output file — and nobody inspects forecast
output for duplicate dates.

### 6.8 The first few fitted points are garbage

The first sample of a differenced model **has no history to use** (the AR term wants
`x_{t-1}`, which does not exist at t=0), so the model emits a meaningless initial estimate:

```
2004-01-01   740    0.000000      <- first point, prediction is 0
2004-02-01   745  1109.018905     <- second point, 1109 against an actual 745
2004-03-01   746   749.997400     <- sane from the third point on
```

⇒ The usual treatment is to blank the leading points. **This is the "runs, but the output
needs manual repair" pattern**: nothing raises, the plot draws — but leaving those values in
stretches the vertical axis of the whole chart.

## 7. An additive decomposable model

### 7.1 What the autoregressive family cannot do

Three constraints:

1. **ARMA wants a stable series, and real data rarely obliges**
2. **ARIMA is linear, and it wants equally spaced observations** — if x1 and x2 are an hour
   apart, so must x2 and x3 be
3. **Gaps have to be filled by interpolation, and the fitted parameters then rest on
   invented values**

Two plainer differences:

- **Following**: five days up predicts a sixth day up
- **Output shape**: an autoregressive model gives **one number**; an additive decomposable
  model gives **a band around a line**

> **The criterion here is the shape of the output, not the accuracy.** When the question
> from the business side is "how bad can this get", one point estimate and one interval are
> not the same answer, and that difference outranks the second decimal.

### 7.2 The model

$$y(t) = g(t) + s(t) + h(t) + \epsilon$$

| Term | Name | What it holds |
| :--- | :--- | :--- |
| $g(t)$ | trend | the **non-periodic** movement |
| $s(t)$ | seasonality | the **periodic** movement |
| $h(t)$ | events | irregular occasions — holidays, sale days |
| $\epsilon$ | error | what the model does not describe |

Three things it is built to survive: **missing data**, **shifts in the trend**, and
**outliers**.

> **Why the additive structure is the headline feature**: additive means **each term can be
> drawn on its own**. The component plot can lay trend, weekly, yearly and holidays side by
> side precisely because they were summed in the first place. **Legibility — being able to
> show a stakeholder which part came from where — is the main reason this model is used in
> industry.**

### 7.3 The sum is literal in the output table

```
forecast['additive_terms'] = forecast['weekly'] + forecast['yearly']
forecast['yhat']           = forecast['trend']  + forecast['additive_terms']
```

and with events declared:

```
forecast['yhat'] = forecast['trend'] + forecast['weekly'] + forecast['yearly'] + forecast['holidays']
```

One row, checked term by term:

| Field | Value |
| :--- | ---: |
| `trend` | 7.188899 |
| `weekly` | 0.048297 |
| `yearly` | 0.969768 |
| `additive_terms` | 1.018065 |

`0.048297 + 0.969768 = 1.018065`, and `7.188899 + 1.018065 = 8.206964`, which is the `yhat`
on that row. **The equation holds arithmetically, not as a metaphor.**

### 7.4 Four methods are the whole interface

| Method | Does | Note |
| :--- | :--- | :--- |
| `Prophet(...)` | construct | every parameter is passed here |
| `fit(df)` | fit | the input takes **exactly two columns, `ds` and `y`** |
| `make_future_dataframe(periods=N)` | build the future axis | **includes the historical dates by default** |
| `predict(future)` | predict | returns a **new** frame with `yhat`, components and intervals |
| `plot_components(forecast)` | decompose | draws trend / weekly / yearly |

**The default in `make_future_dataframe` is a real trap.** Writing `forecast` straight to
disk produces history *and* future, not the horizon alone. The upside is that historical fit
is visible for free; the downside is a submission with a few hundred extra rows.

### 7.5 The output columns

| Group | Columns | Meaning |
| :--- | :--- | :--- |
| axis | `ds` | timestamps |
| trend | `trend`, `_lower`, `_upper` | trend |
| prediction | `yhat`, `_lower`, `_upper` | prediction and interval |
| weekly | `weekly`, `_lower`, `_upper` | day-of-week effect |
| yearly | `yearly`, `_lower`, `_upper` | day-of-year effect |
| additive | `additive_terms`, `_lower`, `_upper` | weekly + yearly |
| multiplicative | `multiplicative_terms`, `_lower`, `_upper` | **empty under an additive model** |

**19 columns = 1 + 3x6.** Declaring events widens it to 28: **each event name becomes three
columns** (value, lower, upper) plus a combined `holidays`, so the width is
`3 x event_types + 3`.

> **The three empty multiplicative columns are usable as a self-check**: if they carry
> values, the model is not additive and the `yhat = trend + weekly + yearly` arithmetic above
> no longer holds.

### 7.6 g(t): piecewise linear, or saturating

**Piecewise linear (default)**: fit a piecewise linear function to the trend. **A linear fit
minimises the influence of unusual points and gaps.** The joints between the pieces are the
changepoints.

**Logistic**: for growth with a ceiling. The example that makes it concrete — app downloads
in a region cannot exceed the number of phone users in that region. **That ceiling is not
something the model can learn; it is supplied by someone who knows the domain**, and it is
called the carrying capacity.

```python
capped_input["cap"] = ceiling
capped_input["floor"] = floor
capped = Prophet(growth="logistic", ...)
future["cap"] = ceiling      # the future rows need it too
future["floor"] = floor
```

Four details:

1. `growth` defaults to `'linear'`; only `'logistic'` needs `cap`
2. **Every row needs a cap**, but it **need not be constant** — a growing market can carry a
   growing ceiling
3. **`floor` is optional**; the logistic default minimum is 0
4. **Saturating decay** works the same way, with a floor instead of a ceiling

**Not setting a floor has a cost**: growth flattens near the ceiling, and a long extrapolation
can bend down through values that make no sense.

Measured, same series, 365 days out:

| Model | Trend at the end | Share of the ceiling |
| :--- | ---: | ---: |
| logistic | 306,830,413 | 53.2% |
| linear | 328,853,862 | 57.1% |

> **The ceiling is an input, not a finding**: the logistic curve bends because it was handed
> a number, and **a wrong number bends it just as smoothly.**

### 7.7 Changepoints

**Detection.** **Twenty-five candidate changepoints are placed uniformly over the first 80%
of the history**, and their magnitudes $\delta_s$ are regularised by a sparse (Laplace)
prior, which shrinks most of them towards zero.

> **Why only the first 80%**: the last fifth holds too few observations to confirm a
> changepoint placed inside it, and a changepoint near the end sets the slope that gets
> extrapolated. **The twenty-five are candidates** — most of them never participate.

**Piecewise trend.**

$$g(t) = \left(k + \sum_{s \in S} \delta_s \cdot \mathbb{I}(t \geq s)\right) \cdot t
       + \left(m + \sum_{s \in S} \gamma_s \cdot \mathbb{I}(t \geq s)\right)$$

| Symbol | Meaning |
| :--- | :--- |
| $k$ / $m$ | base slope / base intercept |
| $\delta_s$ | **the change in slope at changepoint s** |
| $\gamma_s$ | **the offset that keeps the function continuous** |
| $\mathbb{I}(t \geq s)$ | indicator — active only after the changepoint |

> **$\gamma_s$ is the term that gets skipped and the one that shows the intent**: changing
> only the slope would tear the curve apart at the joint, and $\gamma_s$ sews the two halves
> back together. **What changes is the slope, not the value.**

**Extrapolation.** **The future continues the slope after the last changepoint** — that is,
**it assumes no further changepoints.** This fixes the model's character on long horizons:
it will not predict a turn, it extends the most recent slope indefinitely.

**The parameters:**

| Parameter | Description | Default |
| :--- | :--- | :--- |
| `growth` | `'linear'` or `'logistic'` | linear |
| `changepoints` | an explicit list of candidate dates (**given one, detection is off**) | None |
| `n_changepoints` | how many candidates to place automatically | 25 |
| `changepoint_range` | the fraction of history to place them in | 0.8 |
| `changepoint_prior_scale` | flexibility — **larger means a more flexible curve** | 0.05 |

**Tuning**: too many changepoints **overfit** (the curve starts learning noise); too few
**underfit**. A workable range is **25 to 30**.

Three prior scales travel together: `changepoint_prior_scale` (trend),
`seasonality_prior_scale` (seasonality), `holidays_prior_scale` (events).

### 7.8 Measured: are the planted changepoints found

`04_prophet_trend_seasonality_changepoints.py` runs against a series with **four
changepoints and five slopes fixed in the generator**:

| Planted date | New log slope | Nearest detected | Gap, days |
| :--- | ---: | :--- | ---: |
| 1994-06-01 | -0.00021 | 1994-06-21 | 20 |
| 2000-03-01 | +0.00058 | 1999-09-23 | 160 |
| 2005-11-30 | -0.00034 | 2005-11-10 | 20 |
| 2012-06-06 | +0.00041 | 2011-12-29 | 160 |

**All four planted changes are matched within the 200-day tolerance, and the fitter was
never told where to look** — it places candidates on a grid and shrinks the ones the data
does not pay for.

Now the price of flexibility:

| Prior scale | Changes > 0.01 | Planted matched | **Unplanted** | In-sample RMSE |
| ---: | ---: | ---: | ---: | ---: |
| 0.01 | 13 | 4 / 4 | **7** | 11.72 |
| 0.05 | 17 | 4 / 4 | **11** | 11.50 |
| 0.50 | 22 | 4 / 4 | **16** | 11.48 |

⇒ **The four real changes are found at every setting. What a looser prior buys is the last
column.** A looser prior always fits history better, and it pays for that fit with slope
changes the generator never made.

**One measurement worth keeping separate.** On this series the fitted yearly term recovers
only a part of the planted cycle:

```
term                   sd                   range
series              76.63           98.7 .. 441.5
trend               75.66           99.6 .. 413.8
yearly cycle         1.15             -1.8 .. 2.2
remainder           11.50
```

The planted cycle is worth about **15.3 points** either side of the trend; the fit recovered
**2.2**. The reason is a units mismatch: **the cycle repeats every 250 rows and the rows are
business days, while the fitted seasonal term is indexed by calendar date.** The two run at
slightly different rates, so the match is partial. `seasonal_decompose` at `period=250`
(section 3.4) has no such problem, because it counts rows.

> Note also how the shares were computed. Against the raw series the cycle holds 0.0% of the
> variance, which says nothing — **the trend spans four hundred points and the cycle spans
> four.** Subtracting the trend first makes the comparison mean something.

### 7.9 s(t): a Fourier series

$$s(t) = \sum_{n=1}^{N} \left( a_n \cos\left(\frac{2\pi n t}{P}\right)
                             + b_n \sin\left(\frac{2\pi n t}{P}\right) \right)$$

$P$ is the period — **365.25 for a yearly cycle, 7 for a weekly one** — and the fit
estimates $[a_1, b_1 \ldots a_N, b_N]$.

**Choosing the Fourier order N**:

> If the high-frequency content is judged to be noise, take N low.
> If it is not noise, take N high and gain accuracy.

> **This is a design that hands the judgement back to the analyst**: the library does not
> decide whether the small wiggles inside a year are signal, it asks for an integer that
> states your view.

**Additive or multiplicative**: **additive by default**; multiplicative requires an explicit
`seasonality_mode='multiplicative'`.

**How to read the weekly component**: a Monday value of `0.035` means **add 0.035 on top of
the trend**; a Saturday value of `-0.3` means **subtract 0.3**.

**Custom cycles**: `add_seasonality(name='monthly', period=30.5, fourier_order=5)`.

### 7.10 h(t): events

> Holidays and large events are time factors in their own right. **The days around such
> events are considered separately**, and additional parameters are fitted to model their
> effect.

**The hard part is that many events do not fall on a fixed date** — one moves to the second
Sunday of a month, another follows a lunar calendar. ⇒ Hence the design: **the user supplies
a table of events**, rather than the library shipping a perpetual calendar and guessing.

The table has a name column, a date column, and two window columns:

```python
events = pd.DataFrame({
    "holiday": "promotion",
    "ds": pd.to_datetime(flow_truth["campaign_days"]),
    "lower_window": 0,
    "upper_window": 0,
})
```

> **The table must contain every event that occurs — in the history *and* in the period being
> predicted.** The reason is blunt: **a model cannot predict an event it does not know is
> coming.**

**`lower_window` / `upper_window` set how far the influence spreads** before and after the
date. They are not limited to 0 and 1. A useful image: **treat the event as a bump, with the
event days as the peak and the two windows as its spread.**

**Effects add up when a day belongs to more than one event.** From a real fit:

```
             ds   playoff  superbowl
2190 2014-02-02  1.228031   1.201321      <- both non-zero: two events on one day
2191 2014-02-03  1.901884   1.451541      <- the spill-over day from upper_window=1
2532 2015-01-11  1.228031   0.000000      <- one event only
```

Three things readable straight off it:

1. **One event has one fitted value**: every "event day" is `1.228031` — that is the fitted
   parameter
2. **The day after is worth more than the day itself** (1.901884 > 1.228031). **The data said
   that, not the modeller**
3. **Overlapping days sum**: `1.228031 + 1.201321 = 2.429352`

> **⚠️ Fitted event parameters move a little between library versions and optimiser runs.**
> The same code on the same data can give `1.217571` where another run gives `1.228031`.
> **Cite them with the run they came from; they are not theoretical constants.**

### 7.11 Measured: what naming the events is worth

The generator plants four promotion days at a lift of `1.55`:

| Date | Fitted lift | Planted lift |
| :--- | ---: | ---: |
| 2013-11-11 | 1.37 | 1.55 |
| 2013-12-12 | 1.41 | 1.55 |
| 2014-06-18 | 1.38 | 1.55 |
| 2014-08-08 | 1.45 | 1.55 |

And the error, split by day type:

| | RMSE on those four days | RMSE elsewhere |
| :--- | ---: | ---: |
| **Events declared** | **23,172,549** | 42,710,487 |
| Not declared | 136,764,812 | 42,749,153 |

⇒ **Naming the four days moved the error on those four days and left every other day
alone. That is what makes them events rather than outliers.**

### 7.12 Where this model stops

| | |
| :--- | :--- |
| **Strengths** | **Trend, seasonality and event effects without feature engineering**; legible components; few dependencies on external inputs |
| **Limits** | **Cannot use any other information** — not item attributes, not store attributes, not promotion budgets; limited handling of non-time-related noise; **events must be supplied by hand** |

Three models, positioned:

| Model | Character |
| :--- | :--- |
| **Prophet** | most legible; changepoints and piecewise fitting; built-in event and saturation handling; flexible parameters |
| **ARIMA** | leans on statistical properties; **fits one global linear relation** across all history |
| **LSTM** | **can absorb more inputs, explains itself least** |

**The verdict worth keeping verbatim**:

> **Neither is absolutely better. It depends on how well the model matches the structure of
> the data.**

> **That "cannot use any other information" line sets up section 9**: this model eats two
> columns and therefore **knows nothing except time**. On the panel here, doing *only* time —
> but doing it more thoroughly — scores better, because the structure of that panel really is
> almost entirely in the calendar.

### 7.13 Measured: a negative result on a short series

Forced onto the 198-row series — 275 days, **and a generator with no yearly component at

- the fitter **returned a yearly component anyway**, swinging `-6.50 .. 9.73`
- **the series it was extracted from has a standard deviation of 4.24**
- so **the component is larger than the series**, which is only possible because another
  term moves against it

On a held-out tail:

| | Holdout RMSE over 50 days |
| :--- | ---: |
| Yearly on | **8.03** |
| Yearly off | **7.18** |

⇒ **A component covering less than one full period is fitted to whatever shape the sample
happens to have**, and the thing that shows whether it was worth anything is the holdout, not
the fitted curve.

## 8. Windowing and split discipline

### 8.1 The bridge into supervised learning

A series has no feature columns. A **sliding window** makes them: put the previous few
observations of a row into that row as inputs.

```python
def series_to_supervised(values: np.ndarray, window: int, horizon: int
                         ) -> tuple[np.ndarray, np.ndarray]:
    """Turn one long series into rows of (window observations -> next horizon observations).

    Every row overlaps the next by window - 1 observations. That overlap is the
    whole reason the split later in this script has to be made by time: two rows
    drawn from neighbouring positions are not two independent examples, they are
    the same stretch of history shifted by one step.
    """
```

`06_lstm_windowed_forecast.py` runs it at `WINDOW = 14`, `HORIZON = 1`:

```
427 observations -> 413 rows of 14 inputs and 1 target
row 0 covers 2013-07-01 .. 2013-07-14, predicting 2013-07-15
row 1 covers 2013-07-02 .. 2013-07-15, predicting 2013-07-16
the two rows share 13 of their 14 inputs, and row 0's target is one of row 1's inputs
```

A recurrent layer wants its input shaped **[samples, timesteps, features]**, which is what
the `unsqueeze(-1)` in the script produces.

### 8.2 Measured: a random split is wrong here

413 rows, 60 held out, two ways of choosing which:

| Split | Observations the test rows touch | **Also present in a training row** |
| :--- | ---: | ---: |
| **Random** | 359 | **359 (100%)** |
| **By time** | — | **14** (the boundary, unavoidable) |

**Under a random split, every single observation the test rows touch also appears in a
training row.** And **59 of the 60 test rows have an immediate neighbour in the training
set**, differing from it by one step.

⇒ A score measured on those rows answers **how well the model interpolates inside history it
has already read** — which is not the question a forecast asks.

The counting is exact rather than estimated:

```python
def shared_observation_count(left_rows, right_rows, window, horizon, total) -> int:
    """Count observations of the original series that appear on both sides of a split.

    A row index says which stretch of the series a row covers, so membership can
    be counted exactly rather than estimated: mark every observation each side
    touches, and intersect the two sets.
    """
```

### 8.3 Scale from the earlier side only

```
scaling centre 321,299,237 and spread 75,380,048, both computed on training rows only
computing the centre on every row instead would have used 322,119,055,
a 0.26% shift that carries information from the test period into every training row
```

0.26% sounds like nothing. **The size of the leak is not the point; the existence of it is.**
It stops the holdout from being a holdout.

### 8.4 The network, and two baselines that need no training

A single LSTM layer plus a linear head — **9,841 parameters, 120 epochs, full batch** — is
deliberately small, because **the network is not what this script is about.** What matters is
what it is compared against:

| Route | Holdout RMSE over 60 days | Relative |
| :--- | ---: | ---: |
| **Planted periodic factors** (the ceiling) | **28,289,609** | **1.00x** |
| Recurrent model | 32,601,665 | 1.15x |
| Same weekday last week | 56,013,383 | 1.98x |
| Yesterday repeated | 73,887,789 | 2.61x |

**Two readings:**

1. **The network did learn the weekly rhythm** — 2.6x better than repeating yesterday, 2x
   better than repeating last week. **A 14-day window contains two whole weeks, so the weekly
   cycle is visible inside every single row.**
2. **It did not beat a model that only multiplies** — because **it never sees a calendar.**
   The month-position effect reaches it only through whatever the last fortnight happens to
   imply.

⇒ **A window carries the cycles that fit inside it. What does not fit inside it is simply not
there.**

### 8.5 The training-set score is not a forecast

| | RMSE |
| :--- | ---: |
| Training rows | 23,621,720 |
| Holdout rows | 32,601,665 (**1.38x**) |

**The first number is the one a plot of predictions over the training period shows** — and it
exists before any forecast has been made.

> A common shape of the mistake: train, then call `model.predict(train_x)`, then draw the
> predictions over the original series. The two lines hug. **That picture is not evidence** —
> it shows that the model memorised its training data.

Two errors that usually travel with it: **using a `tanh` activation without scaling the
inputs** (the activation saturates at ±1 while the data is in the hundreds), and **not
seeding**, which leaves no number that can be quoted twice.

## 9. Periodic factors: the route with no model in it

### 9.1 Why the autoregressive route leaves something behind

Three criticisms of a plain ARIMA solution on a panel like this one:

> 1) **too simple for what is actually going on**
> 2) **the Monday-to-Sunday structure is not being used**
> 3) **special dates are not considered** — holidays, rate-setting days

**The second one is the turn.**

A fair objection: the forecast plot clearly shows a seven-day wave, so how is the weekly
structure "not being used"?

> Because **an autoregressive model learns "the value seven steps ago", not "today is a
> Monday".** The two look alike on tidy data and mean different things:
> the first depends on **an unbroken chain of history** — drop one day and the chain shifts —
> while the second depends only on **the calendar**. That 20 September is a Saturday has
> nothing to do with what happened on 19 September.

### 9.2 The statistics that stand in for features

> Simple statistics can serve as features and carry real information:
> 1) **the median** — the middle value, and **robust**
> 2) **the mean** — representative when the distribution is roughly normal
> 3) **nearby observations** — **the closer to the target, the more it says**

**Where the method applies, and where it stops:**

> Many quantities are plainly periodic — footfall, payments. **Fix the cycle length** (7 days,
> 30 days), and confirm it with a decomposition. **The weakness is that holidays and one-off
> events are not accounted for.**

### 9.3 The smallest complete example

Three weeks of daily footfall, predicting the fourth:

| | Mon | Tue | Wed | Thu | Fri | Sat | Sun | **Week mean** |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Week 1 | 20 | 10 | 70 | 50 | 250 | 200 | 100 | **100** |
| Week 2 | 26 | 18 | 66 | 50 | 180 | 140 | 80 | **80** |
| Week 3 | 15 | 8 | 67 | 60 | 270 | 160 | 120 | **100** |

**Step 1 — the factors**: average by weekday, then divide by the overall mean.

| | Mon | Tue | Wed | Thu | Fri | Sat | Sun |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **Mean** | 20.33 | 12 | 67.67 | 53.33 | 233.33 | 166.67 | 100 |
| **Factor** | **0.22** | **0.13** | **0.73** | **0.57** | **2.50** | **1.79** | **1.07** |

Checked: Monday's mean is (20+26+15)/3 = **20.33**; the overall mean is
(100+80+100)/3 = **93.33**; 20.33/93.33 = **0.218 ≈ 0.22**; 233.33/93.33 = **2.50**;
166.67/93.33 = **1.786 ≈ 1.79**.

**Step 2 — the base**: take **100** — a representative level, **and this step involves a
human judgement.**

**Step 3 — base x factor**:

| | Mon | Tue | Wed | Thu | Fri | Sat | Sun |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **Week 4** | **22** | **13** | **73** | **57** | **250** | **179** | **107** |

> **The factors read straight off**: Friday is **2.5x** the average level and Tuesday is
> **0.13x** — **Friday is nearly nineteen times Tuesday. No autoregressive model recovers
> that as a calendar fact.**

### 9.4 Five steps for a whole month

The example above handles one cycle. Predicting each day of a month needs a second one
layered on top:

| Step | What |
| :--- | :--- |
| **1** | Compute the **weekday factors** |
| **2** | Compute the **mean for each day of the month** (the 1st, the 2nd, …) |
| **3** | **Count how often each weekday falls on each day of the month** |
| **4** | **Use the weekday factors to get a weighted mean — the base per day, with the weekday effect removed** |
| **5** | Predict from that base and the weekday factor |

> **Steps 3 and 4 are where the substance is, and they are the ones that get skipped.**
>
> "The average for the 5th of the month" is a **biased** number: historically the 5th may have
> landed on a Friday twice (a peak) and a Tuesday once (a trough), so that average already
> carries the weekday effect. **It is not the level of "the 5th".**
>
> **Step 3 counts the collisions and Step 4 divides the weekday effect back out.** That is what
> "removing the influence of the periodic factor" means in practice.
>
> **In one sentence: strip the weekday effect out of the day-of-month averages, compute the
> base, then multiply the weekday effect back in. Skipping it counts the weekday effect
> twice.**

### 9.5 Three implementations

`05_periodic_factor_baseline.py` puts all three side by side. They are not three parallel
options — they are one idea after two rejections.

**One: additive dummies.**

```python
ols = smf.ols(f"{column} ~ C(weekday) + C(day)", data=train.reset_index()).fit()
```

`C()` treats the integer columns as categorical, giving every weekday and every calendar day
its own indicator. The structure is **additive**: `prediction = intercept + weekday effect +
day effect`. It is simple, and every coefficient is readable.

**Why it is the wrong shape here**: it turns the periodic factor into **one more feature fed
to a regression**, and once inside a regression the two effects **add**. But the structure of
this data is **multiplicative** — **"Saturday" takes about 30% off the whole level; it does
not subtract a fixed amount.**

**Two: ratio factors, one effect at a time.**

```python
def ratio_factors(frame: pd.DataFrame, column: str) -> tuple[float, pd.Series, pd.Series]:
    """Take each effect on its own: group mean divided by overall mean.

    This is the estimate that reads as obviously right. It is exact only when
    every weekday meets every day of the month equally often, and over a window
    of a few months it does not: the imbalance leaks part of one effect into the
    other, which the last step of this script measures.
    """
```

No model object anywhere — `groupby`, a division, a `map`, a multiplication.
**Its flaw is exactly what steps 3 and 4 exist to fix**: each set of averages is contaminated
by the other.

**Three: joint fitting by alternation.**

```python
def alternating_factors(frame: pd.DataFrame, column: str,
                        rounds: int = ALTERNATING_ROUNDS
                        ) -> tuple[float, pd.Series, pd.Series]:
    """Fit both multiplicative effects together, by holding one fixed while updating the other.

    Each round divides the observed value by what the other effect already
    explains before averaging, so a weekday that happens to fall on month ends
    more often is no longer credited with the month-end lift. Renormalising after
    every update keeps the level from drifting into the factors, which is what
    makes the two rounds comparable.
    """
```

Three design points:

| Design | Why |
| :--- | :--- |
| **Twenty alternating rounds** | Each factor is a condition of the other, so they can only be approached in turn |
| **Renormalise to mean 1 after every update** | Otherwise one set can be multiplied by ten and the other divided by ten with the product unchanged — the values stop meaning anything (**scale is not identifiable**) |
| **`eps=1e-8`** | Keeps the denominator away from zero |

> **This is the same idea as alternating least squares in matrix factorisation**: when two
> groups of unknowns are entangled, **fix one and solve for the other, then swap.** The
> renormalisation solves the same scale-identifiability problem that appears there. The code
> shares nothing — one completes a matrix, this one fits two sets of one-dimensional factors.

Training 153 days, holding out 31, against factors written into the generator.

**Recovery of the factors** (after normalisation, compared entry by entry):

### 9.7 Measured: what the decoupling correction is worth here

The script quantifies the contamination directly:

| Weekday | **Mean month factor met** | Ratio estimate | Joint estimate | Planted |
| :--- | ---: | ---: | ---: | ---: |
| Mon | 0.9962 | 1.1554 | 1.1716 | 1.1734 |
| Tue | 1.0046 | 1.2662 | 1.2435 | 1.2240 |
| Fri | 0.9823 | 0.9182 | 0.9257 | 0.9509 |
| Sat | 0.9966 | 0.7102 | 0.7148 | 0.7182 |

**Across the seven weekdays the mean month factor met spans only 0.0224** — **five months of
dates very nearly balance themselves.**

⇒ **The correction is worth having and it is not worth much on this window** (mean error
0.0185 → 0.0129). **On a shorter window, or on a calendar with holidays removed, the same
argument gets larger.**

> **This is a case for keeping "the mechanism is right" and "the gain is large" as separate
> claims.** The joint fit genuinely removes the bias in the ratio estimate. **How much bias
> there was to remove is a property of the data, and cannot be assumed.**

### 9.8 Two constraints worth asserting

- **The seven weekday factors average to 1, so they sum to 7**
- **The day-of-month factors average to 1**

That is precisely what `weekday_factor /= weekday_factor.mean()` guarantees.
**Written as an assertion, a botched normalisation fails on the spot.**

### 9.9 Confidence: computing which days cannot be trusted

Every method so far returns a point estimate. A confidence score turns "which days are
unreliable" into something printable.

**Volatility**: the standard deviation, or the coefficient of variation, of each factor set.

**Score**:

$$\text{confidence} = \max(0,\ 100 - k \times \text{volatility})$$

**Combining the two factor sets**:

$$\text{final confidence} = \min(\text{confidence}_{\text{weekday}},\ \text{confidence}_{\text{day}})$$

> **The minimum, not the average.** The two factors are **multiplied** to produce a
> prediction, so if either is unreliable the product is unreliable. **Averaging would dilute
> exactly the signal being looked for.**

**Bands**: high confidence (70–88) for frequent, stable combinations; low confidence (<50)
for sparse data or visibly non-periodic behaviour. **Days with little history need a floor
under their score.**

**The sparsity is real and measurable.** Over 184 training days, **the 31st occurs 4 times**
and the 29th and 30th 5–6 times, while every day from the 1st to the 28th occurs 6 times.
For a 30-day horizon **the 31st never needs predicting** — the days that actually suffer are
**the 29th and the 30th**.

### 9.10 Three limits, stated plainly

| Limit | Detail |
| :--- | :--- |
| **No trend** | **Completely ignores** trend and non-periodic change, including shocks |
| **Sparse cells** | **Month-end days have too little history to be reliable** |
| **No interaction** | Combining the two effects **may be too simple to capture how they interact** |

### 9.11 Why this beats the models: the generating mechanism

| | Time series models | Periodic factors |
| :--- | :--- | :--- |
| **What is used** | **The order of the observations** | **Each occasion treated independently** |
| **Dependency** | Today follows from yesterday | Today relates only to **every previous Monday** |
| **Fits** | Prices and similar **continuously dependent** quantities | Cash flow, footfall — **discrete occasions** |

**The criterion, worth memorising as a sentence:**

> **A price series suits a time series model because today's price is built on yesterday's.
> A cash-flow panel suits periodic factors because each day's flow may be produced by an
> entirely different set of people.**

**Pushing that through to the mechanism:**

> The people who transfer money on Monday the 15th and the people who transferred on Sunday
> the 14th **are largely not the same people**. An extra fifty million yesterday does not
> imply an extra fifty million today — **there is no physical channel between them.**
>
> But "Monday" **does** have a channel: **a settlement rule that pays nothing until the next
> business day pushes every weekend transfer into Monday** (section 2.1). Every Monday
> inherits the same backlog.
>
> ⇒ **An autoregressive model learns "yesterday → today", a channel that does not exist.
> Periodic factors learn "Monday → Monday", a channel that does.** That is why a method built
> from a division and a multiplication beats two real models.

**The same argument explains why changepoint detection does not help here.** A changepoint
mechanism is a **piecewise process built on ordered history**, so it does not fit a case
where the comparison of interest is **this Monday against previous Mondays**, or where the
periodicity is fixed but the dependency is not continuous. Changepoints are the strongest
part of the additive model — **but their strength is in following a turn in the trend, and a
stable window has no turn to follow.** All the information is in the position within the week
and the month.

### 10.1 One holdout is not enough

### 10.2 The protocol

def fold_score(series: pd.Series, origin: str, route) -> tuple[float, int]:

### 10.3 Training-period error is a different measurement

Only the three routes that actually fit parameters can be compared this way — "last week
repeated" fits nothing and has no training-period error to quote:

| Route | On training days | Held out, mean | Inflation |
| :--- | ---: | ---: | ---: |
| Periodic factors | 23,174,048 | 29,001,619 | 1.25x |
| SARIMAX, weekly | 69,622,867 | 80,253,663 | 1.15x |
| Additive model | 44,569,842 | 44,991,115 | **1.01x** |

**The three inflate by between 1.01x and 1.25x, so the gaps between them are not preserved.**
Here the two orderings happen to agree — **but they were free not to**, and only the second
column was measured on days no route had read.

### 10.4 Choosing the training window

**A longer training set is not a better one. The window has to match the regime being
forecast.**

A cash-flow panel of this kind falls into three regimes:

| Regime | Period | Character |
| :--- | :--- | :--- |
| **Rapid growth** | 2013-07 → 2014-01 | explosive — driven by a marketing push, **not organic** |
| **Sharp fall** | 2014-01 → 2014-03 | **a week-long national holiday collapses transaction volume** |
| **Stable** | **2014-03 → 2014-08** | settled |

**⇒ Model the third regime only (184 days).** Three reasons:

1. **One model fitting three regimes at once has them interfering with each other**
2. Fit on the stretch whose character matches the period being predicted
3. **Inertia**: the forecast period correlates most with the most recent data

**The controlled experiment — only the start date changes:**

| Variant | Training data | **Score** |
| :--- | :--- | ---: |
| **A: everything** | 427 days | **92** |
| **B: stable regime** | **184 days** | **108** |

**Same model, same parameters, sixteen points.** It turns "data selection matters more than
model selection" into a number that can be checked.

**A decomposition shows the same thing from another angle**: leaving the holiday period in
contaminates both the trend (pushed up, then down) and the residual (**blowing out to ±4e8
where it otherwise sits inside ±1e7**), while the seasonal component is cleanest after March.

> **⚠️ The soft spot in this argument is worth keeping.** Segmented training assumes the
> forecast period belongs to the same regime as the chosen segment — **and that assumption can
> only be checked afterwards.** If the forecast period contains another holiday-scale
> disruption, a model trained on the stable stretch fails across the board. **There is no
> solution here, only a heuristic (inertia).**

### 10.5 Units and format

Five hard requirements for a machine-scored submission of this kind:

1. **comma separated**
2. **no header row**
3. **exactly 30 rows**
4. **dates as `YYYYMMDD`**
5. two amount columns, **to the cent**

**Units are where this goes wrong:**

| Item | Requirement |
| :--- | :--- |
| **Scale** | The amounts belong in the hundreds of millions |
| **Common failure** | **One order of magnitude low scores zero** |
| **Check** | Confirm the forecast **keeps the magnitude of the training data** |

> ⇒ **This is the practical consequence of section 4.4.** A model with d=1 emits **changes**
> (the measured mean after one difference was 446,251 against a level of 274,793,920).
> Submit them without undifferencing and the numbers are two to three orders of magnitude
> small — **a guaranteed zero.**
> **Glancing at the magnitude before submitting is the cheapest insurance available.**

**One thing that misleads**: a sample submission file may show placeholder amounts an order
of magnitude below the real scale. **It is a placeholder, not a target.** And a unit
conversion (cents against currency units) does not need to be applied at all when scoring is
by relative error — **but half the file in one unit and half in the other is fatal.**

**Three things the scoring rule dictates**, given

$$\text{error}_i = \frac{|z_i - \hat{z}_i|}{z_i}, \qquad
\text{total} = \text{inflow score} \times 45\% + \text{outflow score} \times 55\%$$

1. **An error above 30% scores zero**, so "roughly right" is not enough — it has to land
   inside ±30%
2. **Outflow is weighted above inflow.** That is a business priority written into the
   arithmetic: **underestimating inflow costs revenue, underestimating outflow costs
   liquidity**
3. **Relative error makes small days harder.** Ten million off is 2.5% on a 400-million day
   and 6.7% on a 150-million weekend

### 10.6 Check the file, not the frame

`07` writes the submission, **reads it back**, and checks the result:

```
pass  row count matches the horizon
pass  dates are distinct
pass  dates are the requested month
pass  no header row was written
pass  three columns
pass  no missing values
pass  no negative amounts
pass  amounts are whole numbers
```

> **Why it has to be read back rather than checked in memory**: **the header, the dtypes and
> the date format are all decided by the write.** Only reading the file confirms them.

**A zero-score checklist**: **magnitude, date format, header row, file encoding.** And a
sense of scale for how much this matters — **ten points of difference can move a leaderboard
position noticeably.**

### 10.7 Estimating the score locally

**The workable method: shift the window back.** Train through the end of one month, predict
the next, and compare against values already in hand. That is an ordinary holdout.

**⚠️ What sounds reasonable and is impossible**: "train on March–August, predict September,
compare against actuals". **The September actuals are the answer being competed for.**

⇒ Same trap as section 6.5, from the other side: **a validation set must be data the model
has not seen.**

## 11. What does not show up in a traceback

This is the section worth keeping. **Every item below runs clean, exits zero, and draws a
plot.**

### 11.1 Three classes of silent failure

**One: the code is wrong.**

| Symptom | Where the crack shows |
| :--- | :--- |
| Hand-rolled dates, several steps pushed onto one day | Repeated dates in the output; **values shifted against their labels** |
| Hand-rolled dates, adding the current month's length | Labels drift; **365 of 365 start dates got at least one wrong** |
| Concatenating the wrong object | An extra, useless column in the output |

**Two: the code is right and the experiment does not stand up.**

| Symptom | Why it is not evidence |
| :--- | :--- |
| Training set only, plotting `predict(train_x)` | It predicted its own training data |
| `get_prediction(start=-30)` for an RMSE | **In-sample** — the fit included those thirty days |
| Yearly seasonality on 198 trading days | **Not one complete yearly cycle exists in the data** |
| Candidate grid sliced with `[:20]` | The "best AIC" came from **a systematically biased subset**, printed as if global |
| A debug limit reading only the first ten chunks | **3.5% of the data** — magnitude right, weekly shape right, only the final score is wrong |

**Three: the conclusion rests on one dataset's coincidence.**

| Symptom | Takeaway |
| :--- | :--- |
| An expected effect that two experiment designs failed to demonstrate | **Write the negative result; do not move the criterion to rescue the story** |
| An expected cost of over-differencing that measured 1.11x across three orders | The size of an effect belongs to the data — **it cannot be assumed** |
| An expected large gain from decoupling, on a window that nearly balances itself | **Correct mechanism ≠ material gain.** Two claims, stated separately |

### 11.2 One prescription: put the criterion on an intermediate quantity

Everything above shares one property: **nothing raises.** Therefore:

> **Print the intermediate quantities before the run, not after the result looks wrong.**

For time series work, the list is short and specific:

| Print this | Which failure it closes |
| :--- | :--- |
| **Training rows, and the dates they span** | reading 3.5% of the data; a missing final day; a training set overlapping the horizon |
| **Candidates generated, and candidates actually fitted** | a truncated grid; silent mass failure |
| **Length of the date list, and its de-duplicated length** | repeated dates, drifting labels |
| **Row count after windowing** | a window or horizon off by one |
| **Where the validation set came from** | in-sample passing as a backtest |
| **Whether the factors average to 1** | a botched normalisation |
| **The magnitude of the result** | forgotten undifferencing; the wrong aggregation |

### 11.3 Constraints that can simply be asserted

```python
assert len(set(future_dates)) == len(future_dates)                    # distinct dates
assert all(d == d + pd.offsets.MonthEnd(0) for d in future_dates)     # landing on month ends
assert abs(weekday_factor.mean() - 1.0) < 1e-9                        # factors normalised
assert train.index.max() < test.index.min()                           # training precedes holdout
```

### 11.4 Working with a coding assistant

A large part of the code behind this problem was produced by asking a command-line assistant.
Three reproducible lessons came out of it:

| Failure | How it showed | Why nobody caught it |
| :--- | :--- | :--- |
| **One day short** | The last day of the horizon missing | The history was cut a day early, so a 30-period horizon started one day late |
| **Wrong model shape** | Periodic factors implemented as regression features | The regression ran and the output was plausible — **but additive structure against multiplicative data** |
| **Silently reading 3.5%** | Factors computed wrong | A debug limit added alongside chunked reading, never removed |

**None of the three raises an exception.**

The three working habits that address them:

1. **Ask for the approach before the code** — "analyse the approach, do not write code yet"
2. **State the constraints exactly** — periodic factors only, both weekday and day-of-month,
   multiplied rather than added
3. **Ask it to grade itself** — request a confidence score on the proposed approach; that one
   question is what produced the scoring scheme in section 9.9

**And confirm the parameters by hand.** Weights and combination rules arrive with defaults
(an even split) that are usually exactly what needs to be rejected.

> **In one line: between "the generated code runs" and "the generated code is right" sit
> three failures that never raise. Telling them apart takes someone who knows the mechanism,
> plus printed intermediate quantities.**
